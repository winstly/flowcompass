# 任务全流程

<Purpose>
定义任务从接收到归档的完整 9 步流程。覆盖任务拆解、选角组队、执行、Review、验收、评估和归档的全过程。这是 FlowCompass 的核心执行引擎。
</Purpose>

<Use_When>
- 接收到新的用户需求
- 需要了解任务执行的标准流程
- 任务执行中遇到流程问题需要回溯
- 需要跳转到特定阶段继续执行
</Use_When>

<Do_Not_Use_When>
- 只需要了解组织架构——用 org-charter
- 只需要管理 Agent——用 roster-management
- 只需要评估绩效——用 evaluation-system
</Do_Not_Use_When>

<Why_This_Exists>
没有流程的执行是混乱的。9 步流程确保每个任务都被认真对待：从理解需求到最终归档，每一步都有明确的输入、输出和验收标准。Review 打回机制保证质量，弹性组队保证效率。
</Why_This_Exists>

<Execution_Policy>
- 每个阶段必须有明确的产出物
- Review 不通过必须打回，不能跳过
- 首轮引导时 roster.json 为空，由 Claude Code 临时扮演参谋部
- 任务状态变更必须记录到日志
</Execution_Policy>

## 9 步流程

```
接收 → 拆解 → 选角 → 组队 → 执行 → Review → 验收 → 评估 → 归档
  1      2      3      4      5       6        7       8      9
```

### 第 1 步：任务接收

| 项目 | 内容 |
|------|------|
| 输入 | 用户原始需求 |
| 处理 | 参谋部解析意图，确认理解 |
| 输出 | 任务描述 + 预估级别 |
| 关键动作 | 与用户对齐需求，消除歧义 |

### 第 2 步：任务拆解

| 项目 | 内容 |
|------|------|
| 输入 | 任务描述 |
| 处理 | 按金字塔原理拆解为子任务 |
| 输出 | 子任务列表 + 依赖关系 + 优先级 |
| 关键动作 | 标注子任务级别（S/M/L/XL） |

### 第 3 步：选角

| 项目 | 内容 |
|------|------|
| 输入 | 子任务列表 + 所需兵种 |
| 处理 | 查询 talent_pool → 匹配 → 招募 |
| 输出 | 候选 Agent 列表 |
| 关键动作 | 优先复用人才池，不足再招募 |

### 第 4 步：组队

| 项目 | 内容 |
|------|------|
| 输入 | 候选 Agent 列表 |
| 处理 | 按任务依赖关系组建团队 |
| 输出 | 团队编制 + 指挥链 |
| 关键动作 | 每个子任务指定负责人 |

### 第 5 步：执行

| 项目 | 内容 |
|------|------|
| 输入 | 团队编制 + 子任务列表 |
| 处理 | 各 Agent 按兵种职责执行任务 |
| 输出 | 代码产出物 + 执行日志 |
| 关键动作 | 并行任务同时执行，串行任务按依赖顺序 |

### 第 6 步：Review

| 项目 | 内容 |
|------|------|
| 输入 | 代码产出物 |
| 处理 | 狙击手（纪察部）进行 Code Review |
| 输出 | Review 报告（通过/打回） |
| 关键动作 | 打回时附带具体修改意见，回到第 5 步 |

### 第 7 步：验收

| 项目 | 内容 |
|------|------|
| 输入 | Review 通过的产出物 |
| 处理 | 参谋部检查是否满足原始需求 |
| 输出 | 验收报告 |
| 关键动作 | 与用户确认交付物符合预期 |

### 第 8 步：评估

| 项目 | 内容 |
|------|------|
| 输入 | 执行过程数据 + 验收结果 |
| 处理 | 对参与 Agent 进行四维度评分 |
| 输出 | 评估报告 |
| 关键动作 | 调用 evaluation-system |

### 第 9 步：归档

| 项目 | 内容 |
|------|------|
| 输入 | 全部过程文档 |
| 处理 | 经验包打包、Wiki 更新、日志归档 |
| 输出 | 归档记录 |
| 关键动作 | 调用 career-system 处理晋升/淘汰 |

## 任务分级

接到任务后，参谋部先判断复杂度，决定走哪些阶段：

| 级别 | 典型场景 | 走哪些阶段 | Token 预算 |
|------|---------|-----------|-----------|
| S（小修） | 改个 typo、调个配置 | investigation → 完成 | 低 |
| M（中等） | 修 bug、加个小功能 | investigation → requirements → development → testing | 中 |
| L（标准） | 新功能开发 | 全流程 8 阶段 | 高 |
| XL（大型） | 架构重构、系统重写 | 全流程 + 多轮迭代 | 很高 |

### Token 优化策略

- **Skill 精简**：核心逻辑放 SKILL.md（≤200 行），细节放 references/ 按需加载
- **上下文裁剪**：每个阶段只加载当前需要的 agent 人设，不加载全部

| 级别 | 预估工时 | 团队规模 | 示例 |
|------|----------|----------|------|
| S | < 1 小时 | 1 人 | 修 typo、改配置 |
| M | 1-4 小时 | 1-2 人 | 加个小功能、写单测 |
| L | 4-16 小时 | 2-4 人 | 新模块开发、重构 |
| XL | > 16 小时 | 4+ 人 | 系统级改造、新项目 |

## 弹性组队

组队不固定编制，根据任务动态调整：

- **S 级任务**：1 个突击兵即可
- **M 级任务**：1 个突击兵 + 1 个狙击手（可兼任）
- **L 级任务**：2-3 个突击兵 + 1 个狙击手 + 1 个侦察兵
- **XL 级任务**：完整团队，多兵种协作

## Review 打回机制

```
执行产出 → Review
  ↓ 通过        ↓ 打回
  进入验收      附带修改意见
                 ↓
               回到执行（第 5 步）
                 ↓
               再次 Review（最多 3 轮）
                 ↓ 3 轮仍不通过
               升级到参谋部决策
```

打回规则：
- 第 1 次打回：正常返工，不扣分
- 第 2 次打回：记录问题，影响评估
- 第 3 次打回：升级处理，考虑换人

## 首轮引导

当 `.knowledge/org/roster.json` 为空（首次运行）时：

1. **Claude Code 临时扮演参谋部**：仍然必须完整执行选角和组队，不得跳过
2. **执行选角（第 3 步）**：根据任务拆解结果分析所需兵种，为每个子任务招募 Agent，写入 `.knowledge/org/roster.json`
3. **执行组队（第 4 步）**：将团队分配写入 `.knowledge/org/team-board.md`，格式参照 roster-management 的 Team_Board_Format
4. **确认 team-board 非空后才进入执行（第 5 步）**：team-board.md 为空时禁止启动任何执行任务
5. **后续任务走正常流程**：花名册非空后，按标准 9 步执行（含人才池匹配）
